Design proposal · Sherpa

Make the ticket answer
the questions people actually ask.

Sherpa already records the right facts. Today they arrive as one flat markdown page with the same visual weight, the same facts repeated, and the most useful question — where does this land in the code? — answered only after the work is done. This is a proposal for a readable ticket brief, a code map that exists before the diff, and an agent handoff that is short enough to be read.

01The five questions

A ticket exists to let someone decide and act. Every reader asks the same five things.

Q1

Why does this exist?

Problem, user, and what changes if we ship it.

answered30%
Q2

What exists when done?

Deliverables as outcomes, not a task list.

answered38%
Q3

Where does it land?

Files, packages, symbols, contracts, migrations.

answered14%
Q4

How will we know?

Checks and evidence, mapped to deliverables.

answered45%
Q5

What is the state?

Status, now, blockers, worklog, what is next.

answered84%

Sherpa is strong at Q5. The readability problem is that Q1–Q4 are optional prose, and Q3 is reconstructed from the diff after the fact.

04Ticket anatomy v2

The same ticket at a glance: why, outcomes, where, how we know, and what is happening. Depth lives behind folds and links.

Human-authored

Brief

Stable intent. Short by design; link out for depth.

Why problem · user · consequence Context constraints · prior art · links Approach one paragraph, not a spec Out of scope what this deliberately is not Risks blast radius · rollback
Structured, command-updated

State

Never hand-edited; always current; rendered once.

Now one line, always current Deliverables outcomes + nested checks Code map planned vs touched + stats Measurables target · current · evidence Work done PR · branch · commits Worklog journal → sessions → story

Deliverable → check → evidence

This is the chain that makes "done" unambiguous. A deliverable is an outcome; a check is proof; evidence is where the proof lives.

one deliverable, fully evidenced
✓ Web client retries once on a 401 without a redirect
   ✓ unit   web/src/session.test.ts · retriesOnce       CI #412
   ✓ e2e    cmd/e2e/refresh.sh · two expiries          CI #412
   ○ manual  iOS Safari, private mode                  ✋ tick in TUI
   evidence is a command, a test name, a CI run or a checked
   manual step — never a free-text "works".

05The missing "where": plan, touch, drift

The post-edit hook already records touched files and the journal already records diff stats. The missing piece is intention before the diff. An agent declares its change map, then Sherpa reconciles reality against it.

1 · plan

Agent states the map

Before editing, the agent runs shp plan with deliverables, files, symbols and checks.

$ shp plan --stdin deliverables: - Refresh accepts an expired token where: - internal/auth/token.go modify Rotate, Clock - api/auth/handlers.go modify handleRefresh
→
2 · touch

Reality marks itself

Hooks and git diff mark planned files touched, add stats, and catch edits outside the plan.

✓ token.go +64 −12 ✓ handlers.go +38 −4 △ web/app.ts off-plan planned handlers.go: touched
→
3 · reconcile

Submit speaks plainly

Warnings at submit and a drift badge in the TUI. The review brief leads with plan vs actual.

△ 3 files outside the plan △ deliverable 2 has no check △ planned handlers.go not touched

This turns "what additions are being made where" into something a reviewer can inspect before code exists, and something the agent is held to afterwards. It is also the context an agent needs to start well.

08Give the agent the same brief

OpenCode's advantage is compact, timely context. Sherpa can generate that from what it already knows: the ticket, the plan, the touched files and the journal.

shp brief T-0030 — ≤400 tokens, stable order
TICKET T-0030 · JWT refresh · ◐ in progress · S-004
Outcome users stay signed in past access-token expiry without a re-login.
Deliverables 2/3
  ✓ Refresh accepts an expired access token
  ✓ Each refresh revokes the previous token
  ○ Web client retries once on a 401 without a redirect
Next open check #3 e2e — two expiries, no redirect
Where (planned, 1 touched off-plan)
  ~ internal/auth/token.go      modify Rotate, Clock   +64 −12
  ~ api/auth/handlers.go        modify handleRefresh   +38 −4
  ~ web/src/session.ts          modify retryOnce       +18 −9
  △ web/src/app.ts              touched off-plan
Constraints no schema change · token < 1KB · no new deps
Decisions rotate on use, not a timer (12 Oct)
Do not add dependencies · touch billing/ · change token format

injected at session start, after compaction, and by `shp brief`

Integration path

MCP

Typed tools, not shell

Ship shp mcp with brief, claim, plan, log, check, submit, diff_map. Resources expose tickets and the board.

OpenCode

Plugin does the wiring

Inject the brief, capture file edits and test output, record session id, and publish live activity per tool call. Fail open, as today.

Review

A brief, not a ticket

shp review --brief gives the reviewer plan-vs-actual, deliverable coverage, checks, diff and one pointed question.

Live activity instead of a generic spinner

.sherpa/.local/live/<session>.json → TUI
⛰ sherpa · SHP   ␣ claude · editing internal/auth/token.go · 12s   △ drift: web/src/app.ts
the agent is not "working" — it is editing a named file, with a named drift warning

If only three things ship

1. Deduplicate the state and pin the ticket strip.   2. Add deliverables and the code map.   3. Ship shp brief and plan-drift warnings.

10How we know it worked

The 30-second test

1. State the status and whether it needs you — 5s
2. State what "done" means — 15s
3. Name the files that will change — 20s
4. Find evidence for each check — 30s
5. Explain the last decision and who made it — 30s

Signals over time

review latency ↓ · reject rate ↓ · % tickets with a code map at submit ↑
% checks with evidence ↑ · plan drift visible, not silent
"what is this ticket?" questions in review → 0

Guardrails

New fields are additive, never required. shp lint warns; it never blocks. Generated sections are labelled. Human prose stays human — agents propose plan entries, they do not write the brief. Every fact renders once, from one source, in one place.
